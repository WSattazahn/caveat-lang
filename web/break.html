Try to break this

CAVEAT Language makes agents smarter by remembering why. Here is what it promises when evidence is taken back, in pictures, and a checker you can run. Find a case it gets wrong and file it.

The claim in one picture

The claim, word for word

When a program withdraws a piece of evidence, Caveat erases nothing, flags every current value that was computed from it, and lets the program reopen exactly the decisions whose recorded grounds include it, while each past decision keeps the basis it actually had.

Five rules to break

  • R1 Nothing recorded changes

    The withdrawal is added. Nothing is erased.

    Exact ruleEvery observation, every decision's frozen basis and grounds, and every journal entry stay as they were. The withdrawal is added as its own record. (Withdrawal 0.1, step 3)

  • R2 Everything computed from it is flagged

    Values that touched it carry withdrawn. Others don't.

    Exact ruleEvery current value whose lineage or grounds hold the withdrawn evidence carries the caveat withdrawn, including values read through a decision that rested on it. A value that never touched it does not. (step 2)

  • R3 "Rests on" means grounds, exactly

    Flagged when a withdrawn fact is among its grounds. No other way.

    Exact rulerests_on_withdrawn(D) is true when, and only when, the current revision of D has withdrawn evidence in its frozen grounds. (Predicates)

  • R4 Nothing reopens by itself

    A decision reopens when a rule you wrote says so, on the record.

    Exact ruleA withdrawal changes no decision's status. Only a rule or trigger the author wrote reopens one, and the journal records it.

  • R5 A refused event withdraws nothing

    Refused means no trace: every fact stays as it was.

    Exact ruleA withdrawal is part of its event's transaction.

Outside the claim

  • Whether the evidence was true, or the reason for withdrawing it was good. Caveat records both and judges neither (Limits).
  • A program whose own rules choose not to reopen.
  • Saves edited by hand, events refused by a resource cap, and undoing a withdrawal.
The details

A when condition is control, not grounds, so withdrawing evidence that just opened a gate does not make rests_on_withdrawn true. Values computed under that guard still carry withdrawn through their lineage, and has_caveat(STATE, …) answers from grounds. The guard example below shows both. Caveat gives the predicate; a program's author decides what it means. Saves are not authenticated, and the language offers no way to undo a withdrawal.

What happens to a report

The report button opens a GitHub issue with your program, events and the failed rules filled in. You see it on GitHub before anything is submitted. Every report gets a reply saying whether it is a bug, a disagreement with a rule, or outside the claim, and why. A confirmed bug gets a regression test named after it and a patch release, and its reporter is credited in the release record unless they ask not to be. A disagreement with a rule is a question about the language itself, decided in the open (compatibility). You can also file one by hand with the break report template.

How the checker works

After every event it reads the runtime's own snapshot and tests each rule: R1 compares every earlier record with the new snapshot, R2 compares each value's lineage with the withdrawal records, R3 recomputes "grounds hold withdrawn evidence" and compares it with the runtime's answer, R4 looks for an authored reopening behind every decision that reopened, and R5 checks that a refused event changed no withdrawal or decision. To ask the runtime for R3, it adds one display line per decision to your program; those lines change no state, evidence or decision. It checks the cases you run; it is not a proof. The code is break-check.js.
