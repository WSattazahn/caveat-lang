## Proposed bounded intersections

1. **Authentic post-collection save with a still-standing withdrawal.** Start from one genuine trace containing both departed markers and an independently pinned withdrawn occurrence/reason. Preserve its exact save string as the positive control; restore it and run one accepted continuation. On separate copies, try (a) duplicate the same-history marker, (b) make a marker endpoint a held occurrence, (c) use malformed `archive_ref`, (d) repoint a remaining withdrawal endpoint to an already departed occurrence, and (e) remove only its ledger record or only its graph edge. These should be restore refusals under the contracts above. When altering commitment marker bounds, make corresponding grounds/basis edits if necessary so a different subset check does not mask the intended boundary. Do not require identical error text across versions.

   A valid legacy marker without `archive_ref` is an essential positive control. A well-formed but unavailable 64-hex reference is a different case: the syntax alone does not require restore refusal; host reporting must remain conservative when the corresponding archive is absent. Accepted source-possible coordinated history edits are not automatically regressions.

2. **Required reason survives collection, restore and a later read.** Reuse the readable-holder scenario at `withdrawal_collection.rs:134`, add one independent collectible group, and save/restore before the later read and before releasing the holder. Assert that real unrelated collection occurred, while the old concrete subject/reason and original withdrawal tuple remain standing. Compare the restored continuation's current predicate/caveat/citation behavior with the unreloaded session, then release the holder and check the exact archived tuple. A rejected final-binding event with a previously undrained archive prefix should preserve both save and archive contents. This crosses restoration with an actually exercised required-reason path; it is stronger than checking a successful restore only after all relevant records have departed. Keep the graph small and deterministic; existing native tests already cover large chains and broad root classes.

3. **Runtime-produced archive closure after restore, with selective missing/conflicting inputs.** Use real mutual-withdrawal or reading/reason departures plus one unrelated complete component. Retain the host drain, restore the save (fresh archive buffer), and query through the public reporting APIs using the retained archive. Positive controls: original archive resolves the expected identities/payloads; identical duplicates and input reversal retain the same result. Negative variants: omit a required reason record; omit a reachable provenance node; add a conflicting duplicate in both orders. Affected rows must be unavailable/conservative and must not expose fabricated exact relationships; the unrelated valid component should remain complete. Current dispatch behavior must not depend on whether the host supplies archive data.

   Preserve the documented limit: omitting an unrelated, unreferenced historical record cannot be detected as an incomplete session history. A single internally consistent edited payload may remain complete with `authenticated: false`. These acceptance controls prevent the exercise from silently demanding authenticated replay or a reject-all implementation.
