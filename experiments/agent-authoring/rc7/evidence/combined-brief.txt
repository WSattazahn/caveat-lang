# Caveat rc.7 — Combined Evaluation Plan From Muse + Dot Feedback

## Objective

Use the independent feedback from **Muse** and the **Dot agent** to decide what should actually change in Caveat for `0.1.0-rc.7`.

Do **not** begin by implementing their feature requests.

The objective is to determine:

1. What rc.6 already solved through the official agent-evidence starter.
2. What remaining friction is documentation or application-lifecycle design.
3. What represents a genuine language/runtime/tooling limitation.
4. Which proposed additions deserve implementation in rc.7.
5. Which should explicitly be rejected or deferred.

Preserve Caveat's existing invariants while making agent integrations easier and harder to misuse.

---

# Evidence available

## Muse — first build on rc.5

Muse built `assistant_beliefs.cav`, an assistant self-model tracking:

- clarity of user intent
- memory freshness
- trust in tool output
- a strategy decision such as proceed versus clarify

Its original proposals were:

1. stance-less `reveal EVIDENCE;`
2. first-class `abstain`
3. hypothetical execution / `whatif`
4. improved `because` diagnostics
5. flexible string matching in scenarios
6. better `define` versus `fn` diagnostics

Muse specifically did **not** propose:

- weakening observed-before-qualify
- automatic supports/opposes inference
- general effect-level `if/else`

---

## Muse — rebuild on rc.6

Muse then rebuilt the tracker using the official rc.6 agent-evidence starter.

Reported results:

- `validate` succeeds
- `check` has no warnings
- 7/7 application scenarios pass
- the starter's 53 tests pass
- the demo runs end-to-end

Important changes in the rebuild:

- Uses the official `CaveatServer` and `Attempt` instead of a hand-written subprocess client.
- Separates observation from assessment.
- Treats correction as withdrawal rather than erasure.
- Uses explicit reopening policy.
- Uses the starter's rule that an attempt succeeds only when:
  - all required operations succeed, and
  - the relevant current Caveat assessment permits the result.
- Demonstrates that late qualification does not rewrite archived readings or frozen decision grounds.
- Later observations from the qualified evidence source inherit the caveat.

Muse identified one documentation friction:

> the distinction between the evidence template, archived reading occurrences, current dependent values, and future observations was not obvious.

---

## Dot agent — fresh integration using rc.6 starter

The Dot independently tried the official starter.

Reported benefit:

- reused the Python client instead of writing subprocess communication
- reused required-operation bookkeeping
- avoided manually combining operation success with assessment success
- correctly handled a subtle failure:
  - an old approval remained visible after a new observation was rejected
  - the new attempt was still correctly classified as unsuccessful

Reported remaining friction:

> lifecycle management

Specifically:

> assessing twice without reopening produces “Already assessed.”

Dot still had to decide how and when another assessment should become a new revision.

# Phase 4 — Lifecycle management becomes an rc.7 priority

This is the strongest combined issue from Muse v2 and Dot.

The shipped starter deliberately refuses:

```caveat
assess
```

when an assessment remains in force.

That is correct for its authored policy.

The friction is that a fresh integrator must determine **what kind of second assessment they actually mean**.

Document and test at least three cases.

---

## Lifecycle A — Duplicate assessment

Sequence:

```text
observe strong evidence
assess
assess again
```

Expected:

The second assessment remains refused.

This is not a new decision.

Do not make the runtime silently create another revision.

---

## Lifecycle B — New evidence should reconsider the same decision

Example:

```text
observe 85
assess
observe 90
```

The starter currently only automatically reopens on matching opposing observations.

Evaluate an alternate policy using Caveat's existing mechanism:

```caveat
decisions assessment limit 8 reopened by observations;
```

Test whether this cleanly supports:

```text
observe
assess
observe new evidence
assess revision
```

without new syntax.

Compare:

### Policy 1

Reconsider only when explicitly concerning evidence arrives.

### Policy 2

Reconsider whenever any new observation arrives.

Neither is universally correct.

The application must choose.

---

## Lifecycle C — Different task / different decision

A new user task should not accidentally become revision N+1 of an unrelated previous assessment.

Determine the recommended pattern for task boundaries:

- separate decision series
- new session
- identifiers / subject-specific modeling
- another existing construct

Do not silently reuse an old approval for a different subject.

# Phase 10 — Evaluate `whatif`

Muse wants safe counterfactual execution.

First determine what already exists through:

- save
- restore
- second session
- replay
- `serve`

The proposed improvement may be a standardized convenience operation rather than a new reasoning primitive.

---

## Important distinction

These are different:

### Branch from current session

History already contains:

```text
clarity 85
strategy proceed
```

Then hypothetically add:

```text
clarity 40
```

This asks:

> What happens after an additional reading of 40?

### Replace an earlier event

Fork from before clarity 85 and instead send clarity 40.

This asks:

> What would have happened if the original reading had been 40?

Do not claim these are equivalent.

---

## Possible `serve` operation

Evaluate something like:

```json
{
  "op": "whatif",
  "events": [...]
}
```

Possible semantics:

1. clone/fork current session
2. apply hypothetical events
3. return each outcome
4. optionally return snapshot/view
5. optionally return explain
6. discard fork
7. leave live session unchanged

---

## Required isolation tests

Verify that hypothetical execution cannot change live:

- sequence
- elapsed time
- state
- readings
- reading IDs
- decisions
- decision IDs
- identifiers
- caveats
- withdrawals
- reopening records
- journal
- effects
- cues
- save output

Also test:

- accepted hypothetical events
- policy rejection
- input rejection
- evaluation rejection
- limit rejection
- fatal hypothetical path

A fatal hypothetical branch must not destroy the live session.

---

## Do not overclaim

`whatif` can answer:

> What would this policy do from this state under these events?

It cannot answer:

> Would that result be better?

An external evaluator or authored objective is required for that.

# Phase 11 — Reevaluate `abstain`

Do not implement this merely because Muse originally used “clarifying” as a third outcome.

Muse v2 apparently models clarification successfully as an actual strategy decision.

That weakens the argument that:

```text
clarifying
```

must itself be represented as abstention.

Find a genuinely distinct requirement:

> The system has evaluated the substantive decision and deliberately refuses to choose any substantive outcome.

That is different from:

> The system chooses to ask for clarification.

If that distinction matters in a real integration, then design `abstain`.

---

## If justified, specify state machine before syntax

Cover:

```text
none → abstain
abstain → commit
commit → reopen → abstain
abstain → reopen → commit
abstain → abstain
```

Define:

```caveat
committed(strategy)
abstained(strategy)
reopened(strategy)
latest(strategy)
```

for every relevant state.

Also define:

- series limit use
- revision identity
- journal entry
- grounds
- lineage
- retained caveats
- predecessor relationship
- explain output
- save/restore
- automatic reopening

Particularly ensure:

> After a previous substantive commitment is reopened and the system abstains, a host cannot accidentally continue treating that old commitment as the current actionable decision.

If the contract is not clean enough, **do not ship `abstain` in rc.7.**

## D1 — Incorrect `because` citation

Differentiate:

- unknown symbol
- known symbol of wrong kind
- valid citation
- citation not present in lineage/grounds

---

## D2 — `define` versus `fn`

For:

```caveat
define freshness_last() = ...
```

give a targeted diagnostic.

Something conceptually like:

> `define` declares a named expression and does not take parameters. Use `define freshness_last = ...`. Use `fn freshness_last(...) = ...` only for a pure function with explicit parameters.

Do not automatically recommend `fn` when the expression needs to read state/history that a pure function cannot capture.

# What success for rc.7 would look like

Do not judge success by feature count.

A good rc.7 might contain:

- substantially better repeated-assessment guidance
- clearer late-qualification documentation
- stronger integration regression tests
- better diagnostics
- perhaps stance-less observation
- perhaps `whatif`
- no `abstain` yet

if that is what the evidence supports.

Likewise, if testing shows that one of the larger proposals solves a real recurring problem cleanly while preserving Caveat's invariants, implement it.

The goal is:

> Fresh agents should write less support code, make fewer lifecycle mistakes, preserve evidence honestly, and understand why the runtime behaved as it did.

Do not weaken Caveat's guarantees merely to make an integration superficially easier.
