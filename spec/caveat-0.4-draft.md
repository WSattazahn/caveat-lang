# CAVEAT Language Specification — Draft 0.4

This draft adds knowledge-dependent action requirements and source-authored
outcomes to the checked world/action model in Draft 0.3. The executable profile
is `GameSession`, also exposed as `WebGameSession` for WebAssembly. Its host may
render the world, but cannot choose which evidence satisfies a requirement or
which authored outcome follows a commitment.

## 1. Action requirements

```caveat
require navigate_channel observed measured_pulses;
require navigate_channel examined fog_refraction;
```

Each requirement refers to an existing action plan. `observed` requires an
evidence symbol; `examined` requires a caveat symbol. Multiple requirements on
one action are conjunctive: all must hold. Actions with no requirements retain
the existing behavior. Duplicate requirements are rejected.

`observed EVIDENCE` holds when the reached epistemic graph contains a `supports`
or `opposes` edge originating at that evidence. Merely declaring evidence,
mentioning it in a future reveal, or emitting an `observe` animation command
does not satisfy the predicate. Evidence that opposes a claim counts as observed;
observation makes no assertion that a claim is true. Conflicting evidence stays
in the graph.

`examined CAVEAT` holds when the caveat's live attention is `Examined`, as
established by a successful paid inspection or examination. `Examining`,
`Deferred`, and declaration alone do not satisfy it.

The action must also be a member of the current interaction, meet physical world
preconditions, and fit the remaining inspection budget. Future scripted
`select`/`inspect` defaults never establish present knowledge. Declarative rule
and world references are validated globally; conditions read only the executed
prefix.

## 2. Source-authored resolution

```caveat
resolve light_beacon as controlled_arrival when observed measured_pulses;
resolve light_beacon as checked_but_uncertain when examined fog_refraction;
resolve light_beacon as uncertain_signal otherwise;

display controlled_arrival "The measured signal guides the vessel home.";
display uncertain_signal "The beacon shines, but its reading remains uncertain.";
```

An action's conditional resolutions are checked in source order. The first
matching rule wins. Conditions inspect live knowledge immediately **before**
the action executes: evidence generated by the action cannot retroactively
justify that same action.

Every action with resolution rules must have exactly one `otherwise` rule,
placed after all its conditional rules. A fallback-only resolution is valid.
Each conditional rule has one `observed` or `examined` predicate. Repeating an
identical predicate for one action is an error because the second rule would be
unreachable. Outcome identifiers are source-owned labels and can have `display`
text; no new claim or evidence is asserted by naming an outcome.

Resolution does not end the program by itself. It records the latest resolved
action, so an author can use it for intermediate consequences or the final
interaction. An action without resolution rules preserves the existing outcome.

## 3. Transactional execution

`GameSession::apply` checks current availability before changing state. Physical
commands, attention spending, epistemic effects, selection history, and outcome
publish together. A blocked action, out-of-turn request, invalid subsequent
effect, or failed resulting snapshot leaves all state and save bytes unchanged.
The same checks apply to direct host calls; disabling a button is not the rule
enforcement mechanism.

The underlying epistemic evaluator and legacy `Session` still evaluate reasoning
statements. Like topology and physical action plans, these game-profile
declarations are compiled and enforced by `GameSession`; a host using the legacy
evaluator alone is not a conforming runner for this profile.

## 4. Inspection and snapshot contract

The static `CaveatMap` contains `requirements` and `resolutions`. `inspect` returns
rules that mention the requested action, evidence, caveat, or outcome identifier.
This is authoring data and may describe the full source.

The live `caveat-game/0.1` snapshot instead adds these fields:

```json
{
  "blocked_actions": [
    {
      "action": "navigate_channel",
      "reasons": [{"kind": "observed", "symbol": "measured_pulses"}]
    }
  ],
  "outcome": {
    "action": "light_beacon",
    "id": "controlled_arrival",
    "basis": [{"kind": "observed", "symbol": "measured_pulses"}],
    "turn": 6
  }
}
```

`pending.options` contains currently available options. `blocked_actions`
describes unmet epistemic requirements for the current interaction only; it is
empty for a completed session. It does not list future decisions or pretend
that a merely declared evidence symbol has been observed. Physical and budget
blocking continue to use the existing pending-state checks.

`outcome` is `null` until an action with resolution rules commits. Its basis is
the winning predicate, or an empty array for `otherwise`. Future outcome rules
are not copied into the live snapshot's world. A blocked interaction is reported
as `blocked`, never silently converted to `complete`.

## 5. Save identity

Saves retain exact source bytes and the ordered selection log. Restore checks
the source identity and replays every selection through the same requirement,
world, and resolution rules. Editing source conditions or outcome IDs invalidates
old saves; changing the source fingerprint alone cannot bypass the exact-source
check. Replaying the same valid save reconstructs the same outcomes and bases.

## 6. Source presentation

Draft 0.4 also supports checked presentation declarations for world placements,
cameras, overview, and routes. See [presentation.md](presentation.md) for their
grammar and renderer contract. They determine presentation rather than evidence
truth, and cannot satisfy epistemic requirements.
