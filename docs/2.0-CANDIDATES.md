# Caveat 2.0 candidates

Status: a list of changes, not a plan or a promise. Nothing here changes any
1.x release. Started 2026-10-31, when the owner chose to keep a 2.0 list: if
something is not working well and can be improved, Caveat should not hold on
to it.

The [compatibility commitment](COMPATIBILITY.md#versioning-policy) keeps
every 1.x release to additions: the same output bytes, exit statuses and
accept or refuse answers for anything that worked before. Some things that
work badly can only be fixed by changing those. They wait here for 2.0.

## How an item gets on the list

An item is on the list when both hold:

1. Something is wrong or costly today, with evidence: a test, a measured
   number, a finding or an agent run.
2. The fix changes something 1.x keeps. Things 1.x already lets a release
   change (messages, CLI prose, raising a limit, adding a field, code or
   option) are not 2.0 items; they go in a 1.x release.

Each item says what is wrong today, the change, who it breaks, the evidence,
and the 1.x step that comes first. Where a 1.x opt-in exists, 2.0 only flips
the default, and the opt-in keeps loading as a no-op so a 1.x program that
uses it still loads.

The policy also requires a deprecation notice in the release notes at least
one minor before 2.0 removes or changes anything. Each item below needs that
notice in a 1.x release, and a spec PR for its 2.0 meaning, before it ships.

## When 2.0 ships

Owner decision, 2026-10-31: 2.0 switches its defaults all at once, in one
release, and only after each change it makes has shipped as an opt-in in a
released 1.x minor whose release notes announced the change. An item that has
not done both waits for a later major. No date is set.

## Ready: a 1.x opt-in exists or is in review

### 1. Routed rule copies for other members spend the work budget

- **Today.** A rule in a routed block runs once per member. For an event
  routed to one member, the copies for every other member are skipped, but
  each still counts a step against the event's budget of 4,096
  ([Limits](LIMITS.md), "Worst cases"), and so does each step of a procedure
  a skipped copy calls. One routed rule over a few thousand members can
  refuse an event as `limit/work_limit` although only one copy does
  anything.
- **Change.** Copies routed to another member cost no steps by default.
- **Breaks.** A program whose events are refused as `work_limit` only
  because of skipped copies: those events are accepted. No program in the
  repository's sweep (187 programs, 2,393,600 events) reaches that limit, so
  none changed there.
- **Evidence.** The 1.5 opt-in's regression test
  `gap_2b_routed_copies_for_other_members_cost_no_work`
  (`runtime/tests/routed_work.rs`, #409); compiler step 1 (#403), which
  skips evaluating those copies' guards.
- **1.x step.** 1.5 adds the program line `work skips other routes;` (not
  allowed in a module). 2.0 makes it the default and keeps the line loading
  as a no-op.
- **Note.** A skipped copy still does real work when its guard rests on
  something: it keeps that basis on each target. 2.0 keeps that; only the
  step charge goes.

### 2. A minimum or maximum rests on every argument

- **Today.** `min(a, b)` is `if(a < b, a, b)`, and an `if`'s condition reads
  are grounds. A minimum over many readings rests on all of them: in the
  third agent test one answer rested on 94 reports, a reader filtered 24
  retracted reports out of the grounds by hand, and retracting a report that
  was never the lowest flagged everything downstream as resting on withdrawn
  evidence.
- **Change.** A comparison's reads go into lineage only; grounds hold the
  argument returned.
- **Breaks.** Grounds, rests-on-withdrawn flags, undo lists, `in_basis` and
  view bytes of programs that use `min`, `max` or `if`.
- **Evidence.** Third agent test, runs A2 and A4 (round 2).
- **1.x step.** `lowest`, `highest` and `choose` (Choices spec, #405). 2.0
  gives `min`, `max` and `if` that meaning, or retires them in their favor.

### 3. Strict irreversible commits are opt-in

- **Today.** An irreversible commit is refused when its grounds carry a
  caveat it does not name, but evidence that only opens its gate (the guard,
  or a `permitted by` grant) is not asked about unless the series says
  `strict`. A payout can rest on an unchecked email and still be accepted.
- **Change.** Every irreversible series reads its whole lineage.
- **Breaks.** Programs whose irreversible commits pass a gate resting on an
  unnamed caveat: those commits are refused as `caveated_irreversible`.
- **Evidence.** [Strict Irreversible 0.1](../spec/caveat-strict-irreversible-0.1.md),
  "Questions settled" 1, which names the default as a 2.0 candidate.
- **1.x step.** `strict` shipped in 1.4.0.

### 4. Each view is built whole, fresh and mutable

- **Today.** `dispatchView` builds, serializes and parses the whole view
  every event. On the release-gate workload that is about 150 of 261 µs per
  event; parsing the ~13 KB view alone costs about 56 µs, five times the
  11 µs per event target. The patch that carries only what changed averages
  1.4 KB.
- **Change.** The reused view (read-only, unchanged parts shared, built from
  the patch) is the default; fresh objects become the opt-in.
- **Breaks.** Hosts that write to the view, or rely on each view being new
  objects.
- **Evidence.** [View Patch 0.1](../spec/caveat-view-patch-0.1.md), "Cost";
  `bench/carmack/profile.mjs` (fresh 261 µs, reused 168, dispatch alone 110;
  measured locally 2026-10-31).
- **1.x step.** `dispatchView(event, payload, { reuse: true })` (#404).

## Needs design first

### 5. The view is promised byte for byte

- **Today.** View 0.1 output is fixed to the byte, key order and number text
  included (the runtime writes `0.0` where JavaScript writes `0`). Every
  change must produce exact runtime text, which forces raw-text workarounds
  and keeps the runtime from handing structured values to the kit.
- **Change.** Promise the view's value, not its text.
- **Breaks.** Anyone diffing view text or holding byte-for-byte goldens.
- **Evidence.** `kit/test/dispatch-view-reuse.test.mjs` compares against a
  re-stringified parse because of number text; the raw-text path in
  `runtime/src/reactive_view_patch.rs`. Not measured on its own.

### 6. Every view member is computed every event

- **Today.** Binding explanations and commitment grounds are built every
  event whether the host reads them or not. Most of the reused view's
  remaining cost (about 36 µs over dispatch) is comparing each member with
  the last view.
- **Change.** Explanations and grounds come on request.
- **Breaks.** Hosts that read them from each view.
- **Evidence.** View Patch 0.1, "Cost". The split by member is an estimate.

### 7. A state always has a starting value

- **Today.** Every state starts with a value, so a missing input reads as a
  number. In the third agent test an inherited program gave a bridge with
  unrated parts a rating, and the wrong rule ran until a notice exposed it;
  agents worked around it with sentinel values such as 1000 and `_unrated`
  flags.
- **Change.** A state may be declared unset until first set; reading it
  unset refuses the event.
- **Breaks.** Programs and saves that rely on starting values, if 2.0 makes
  unset the default. As an added declaration it could ship in 1.x instead;
  the design decides which.
- **Evidence.** Third agent test, runs A1 and A2 (round 1).

## To consider

### 8. New evidence reopens nothing by itself

- **Today.** A decision reopens only through an authored rule or trigger. In
  the third agent test, one new report had to be added by hand to ten
  decisions' reopen lists.
- **Change.** A decision about a claim reopens when new evidence on that
  claim arrives, unless the program opts out.
- **Breaks.** Decision outcomes and journals broadly.
- **Evidence.** Third agent test, run A1 (round 1).
- **1.x step.** The opt-in in #398. Weaker case than the items above: decide
  after the opt-in has been used.

## Looked at, not 2.0

- **The expansion limit** that refused a nested `min` over eight values:
  fixed in 1.x (#400, D034).
- **Limits** such as the work budget's number: 1.x may raise any of them.
- **Messages and CLI prose** (for example D011's event numbering): 1.x may
  change them.
- **Taking off a declared caveat** (third agent test, run A4): expected to be
  additive in 1.x. It joins this list only if that fails.
- **Saves bound to their exact source**, so a comment-only edit stops a
  restore: a standing owner decision ([Saves](COMPATIBILITY.md#saves-archives-and-source)),
  kept unless the owner reopens it.
- **Free routed copies that keep their basis**: the basis is real work (item
  1, note), so only the step charge is a 2.0 change.
- **A general layer beside a program** ([design note](design/general-layer.md)):
  every step it plans adds to 1.x. The one change that would need 2.0, a rule
  that calls code outside the program, is what that design forbids in every
  version, and requiring a sender on every event is not needed because each
  task sends only its own agent's events.

## What 2.0 still keeps

- Refusal codes. They are permanent: 2.0 adds codes and moves inputs between
  codes only where an item above says so, and renames or removes none.
- A 1.x save restores for the same source, or 2.0 ships a migration that
  turns it into a 2.0 save.
- Every 1.x opt-in line still loads.
