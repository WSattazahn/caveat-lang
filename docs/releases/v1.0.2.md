# CAVEAT Language 1.0.2

**Candidate, not yet published.** This note becomes the release record once
npm publication of caveat-lang@1.0.2 is verified.

1.0.2 is a patch release of 1.0.1. It contains two runtime fixes, D016 and
D018, to changes that [1.0.1](https://github.com/WSattazahn/caveat-lang/blob/main/docs/releases/v1.0.1.md)
introduced, and nothing else. Both affect only programs with a window or
limit. Like 1.0.1, it is cut from the maintenance branch `release/1.0.x`. It adds no language syntax, schema, runtime operation, field,
CLI flag, export, MCP tool or tool argument, and no rejection code. 1.0.0 is not
affected.

## Departure learns of evidence a late qualify adds to a stored record (D016)

1.0.1's D014 fix lets a `qualify` that comes after a guarded observation, and
the `withdrawn` caveat a withdrawal applies, reach the stored observation and
predicate qualifications that list the evidence. It merges the caveat's lineage
and the rule's guard into those records, so they can come to reference evidence
they did not reference before. In 1.0.1 the withdrawal collector, which decides
which retired records are still pinned before departure runs, was not told of
the new reference. A debug build's own consistency check fails at the end of
such an event. A release build, which is what npm ships, runs departure on that
stale index.

In 1.0.2, each record a late qualify reaches is recounted before departure
runs, so the collector's index matches the records again.

**Who can be affected.** Only a program on 1.0.1 that has both of these:

- a window or limit: `renewable … window`, `readings … window` or
  `decisions … limit`;
- a `qualify` or `withdraw` that reaches evidence a guarded rule already read,
  such as `when observed(e)`, `when committed(d)` or `reopen` guards.

No difference in a release build's output has been shown. The fault is in the
index that decides what a retired record still pins, so in some sequence 1.0.1
could let a record depart while a stored record still lists it. 1.0.0 cannot
reach this path, and saves restore unchanged: restore rebuilds the collector
from the records, so a 1.0.1 save restored on 1.0.2 starts from a correct index.

This is finding D016, found by a seeded randomized check of windows and
departure.

## A doubt read through a record keeps its take-back after its evidence departs (D018)

1.0.1's D012 fix leaves a take-back caveat live, rather than kept, in a stored
observation or predicate qualification while the evidence it came through still
has a live relation. When that evidence departs from a window, its relation
leaves with it. 1.0.1 then kept the caveat on current values only. A value read
afterwards through the stored record carried the caveat with no live relation
and nothing kept, so a later `unqualify` could not reach it and a reader could
not tell it from a doubt no evidence carried. That is the shape D012 fixed,
reached through departure.

Take a program with `renewable e window 2`, `on report when observed(e) renew e`,
and a flag and its take-back on `e`. After report, report, flag, report,
report, the second occurrence departs. A value that was current at the
departure lists `flaky` as kept. In 1.0.1, a value read again as
`qualified(1, e)` carried `flaky` without listing it as kept. Unlike D016,
this shows in a release build's output.

In 1.0.2, when a record departs, every provenance that held it keeps each
take-back caveat the record's live relations gave it, stored observation and
predicate qualifications included. A value read afterwards through a record
carries exactly what it would have carried had the record stayed.
[Take-back 0.1](https://github.com/WSattazahn/caveat-lang/blob/main/spec/caveat-take-back-0.1.md),
"Departure and collection", now says so.

**Who can be affected.** Only a program on 1.0.1 with a window, an `unqualify`
or a flag on windowed evidence, and a guarded rule that stores a record over
that evidence. A 1.0.1 save written after such a departure keeps what it
recorded. A host that kept its own event log can repair it by replaying
those events on 1.0.2.

This is finding D018, found by a seeded randomized check of take-back under
windows and departure.

## Tests

The D016 fix carries its regression in `runtime/tests/departure.rs`, named
`a_late_qualification_reaching_a_stored_record_updates_the_collector`, in five
events: `see_e`, `see_f`, a commit guarded on `observed(e)`, a skipped reopening
whose guard read `committed(d)`, then `withdraw e because f` under a guard
reading `f`. It fails on 1.0.1 at the collector's own check and passes with the
fix. It also checks that a session restored from a save agrees with the live
one on every later event.

The D018 fix carries
`a_value_read_through_a_record_after_its_evidence_departed_keeps_the_caveat`
in the same file, which fails on 1.0.1 in a release build, and
`runtime/tests/take_back_windows.rs`, a randomized check of Take-back 0.1
under windows and departure: 200 runs of 60 events with guarded renewals and
reveals, same-named caveats through a guard, late qualifications, withdrawals
under a guard, decisions pinning records, and saves and restores in place.

Both fixes are the same commits as on `main`, picked with `git cherry-pick -x`.
