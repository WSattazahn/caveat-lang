## MCP tools explain when and how to use them

The five existing tools now describe their distinct purposes, input meanings,
result envelopes and exit codes ([PR #229](https://github.com/WSattazahn/caveat-lang/pull/229)):

- `caveat_validate` checks loading and lists declarations.
- `caveat_check` reports authoring diagnostics and explains the optional
  `strict` flag, including how suppressed diagnostics affect the result.
- `caveat_test` explains the nested scenario document, its virtual
  `inline.cav` source, assertions and limits.
- `caveat_explain` describes event replay, decision grounds and history.
- `caveat_dependents` defines evidence, streams, occurrence IDs and caveats
  for a dependency query.

The descriptions distinguish completed operations with nonzero `exitCode`
from bridge failures with `isError: true`. They also explain that calls start
fresh, rejected events remain reported outcomes, and a fatal event stops
replay at the last good state. The input constraints, annotations, result
formats and execution behavior are unchanged. The
[MCP guide](../../kit/docs/MCP.md) adds tool-selection guidance and a complete
scenario example, with instructions for the protocol envelope and metadata.

## `explain` separates three roles for caveats

Human-readable `explain` output now places caveats carried by a decision's
grounds beside that evidence. For example, the umbrella explanation shows
`based on rain_chance@1 (caveats: forecast_is_old)` instead of presenting that
evidence-carried caveat as an authored `retaining:` choice.

A `retaining:` line lists grounds caveats that none of those evidence
observations currently carries. Caveats inherited through a prior decision
or reopening witness appear separately as `also carrying, through its
lineage:`. The commitment-history lines use the same distinction. If a caveat
is both carried and authored, the formatter shows it as carried; if its
qualification was taken back after the commit, it remains visible as retained.

This is a text-formatting correction. The stored decision, frozen grounds,
lineage, JSON explanation and runtime behavior are unchanged. The D007 and
D009 dogfooding regressions cover carried versus authored caveats and caveats
inherited after reopening.

## Documentation and verification

The authoring guide explains how to record why a caveat was left unpursued,
and warns that repeating a plain commitment is fatal: repeated decisions need
a declared decision series or an authored refusal. The getting-started output
and reviewer-decision example follow the corrected explanation terminology.
Published rc.19 save fixtures and archive/dependency comparisons extend the
existing compatibility checks.
The publication closeout adds authentic rc.20 `frost`, `ordered` and
`readiness` saves generated from a fresh installed release. All 13 save-fixture
tests passed, including the retained older releases. These are bounded
compatibility examples, not authenticated histories or universal proof.
For both MCP protocol profiles, the package check now compares the installed
server identity and complete tool catalog with the source manifest and
definitions, retaining the catalog count and SHA-256 in its report.

The Rescue browser harness now retains startup errors, console and failed
request details, page state and screenshots, and closes a context whose
initialization fails. An injected source-load failure checks that reporting
and cleanup on each tested browser. Explicit application boot errors fail
promptly; the existing startup timeout and gameplay assertions remain. This
improves diagnosis of the observed WebKit startup timeout; it does not establish
its underlying cause or add automatic retries.
