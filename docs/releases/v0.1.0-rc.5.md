# caveat-lang 0.1.0-rc.5

The fifth release candidate of the developer kit. It is a **release
candidate, not a stable release**. Like [rc.4](v0.1.0-rc.4.md), it is to be
published to npm with the tag `next`, with the same tarball attached to the
GitHub pre-release `v0.1.0-rc.5`.

**This record was written before publication**, with the pull request that
names the candidate. The release commit is that pull request's merge, so the
[identity](#identity), [gates](#gates) and [npm tags](#npm-tags) below are
marked **TO BE FILLED**, from CI's `kit-package-candidate` for that commit and
from the checks after publication. Until then, rc.5 is on neither npm nor
GitHub, and `npm install caveat-lang@next` installs rc.4.

```sh
npm init -y
npm install caveat-lang@0.1.0-rc.5
npx --no-install caveat init
npx --no-install caveat test umbrella.scenarios.json
```

## What changed since rc.4

Five pull requests were merged after rc.4: #64 to #67, and #69. Two change
the package:

- **`caveat check` reads a chain of `or`**
  ([#67](https://github.com/WSattazahn/caveat-lang/pull/67)). C003 counts a
  top-level conjunct as routing when it is a chain of `or` every disjunct of
  which is a selection, so a rule that selects its member by either of two
  parameters, such as `(first == $index or second == $index)`, is no longer
  reported. C004 now checks every comparison of a parameter with `$index`:
  each top-level conjunct, and each disjunct of such a chain. Before, it
  checked only the first. Before the Rain, a game written in Caveat outside
  this repository, goes from 35 C003 warnings to none.
- **`session.dispatchView(event, payload)`**
  ([#69](https://github.com/WSattazahn/caveat-lang/pull/69)), and the
  runtime's `dispatch_view_outcome`: the dispatch outcome with the view in
  place of the snapshot, which it does not build. For a host that redraws
  from the view, it saved 82 to 144 µs per accepted event against
  `dispatch()` and then `view()`
  ([measurements](../../experiments/performance-opt-0.1/RESULTS.md)).

The packaged specs change with them: Caveat Check 0.1 (C003, C004 and a
Changes entry), Routed Repetition 0.1 section 8, Dispatch 0.1 ("The view
path") and View 0.1. The other three pull requests recorded rc.4 as
published (#64), moved `main` to `0.1.0-rc.5` (#65), and added a
measurement-only performance baseline under `experiments/` (#66), which is
not packaged.

**The package** holds the same 59 files as rc.4, 12 of them changed. Packed
from this candidate's local Windows build, it is about 723.5 kB, 0.8% more
than rc.4's 718,051 bytes. The WebAssembly runtime grows by 8,364 bytes
(rc.4 and rc.5 built the same way). CI's Linux figures go in
[Identity](#identity).

## Compatibility

Programs, saves and events behave as they did in rc.4. What an rc.4 user can
observe is below.

**`caveat check` warnings that disappear** (#67). C003 no longer reports a
rule in a plain `for` block whose guard has a top-level conjunct that is a
chain of `or` of selections, written directly or through a define:
`(first == $index or second == $index) and $e_points == 0`,
`from == $index or via == $index or to == $index`,
`from == from.north or to == $p_slot or from == round($index)`, or
`$p_moved` after `define $p_moved = from == $index or to == $index;`. Such a
program that failed `--strict` may now pass. Dropping `routed by P` from a
block with a rule guarded by `P == $index or Q == $index` is no longer
reported. An allow comment over such a rule now suppresses nothing, so the
`--json` report's `suppressed` list loses its entries. A chain with any
disjunct that is not a selection is still reported, as in
`from == $index or $p_last > 0`, a parameter of another kind, an `and` inside
the chain, or `not (…)`.

**`caveat check` warnings that appear** (#67). C004 applies only where a
`for` block declares an entity of the kind before a top-level member. With
north declared that way before east and south:

- `via == $index + 1 and from == $index` gets C004 on `from`; rc.4 reported
  nothing, and already reported the conjuncts in the other order;
- `from == $index or to == $index` gets C004 on `from` and on `to`, where rc.4
  gave C003, or nothing if C003 was allowed;
- `to == to.$p and (from == $index or to == $index)`, and
  `from == $index or to == $index` on the member's own event (`on $p_move`),
  get C004 on `from` and on `to`; rc.4 reported nothing;
- `from == $index and to == $index` gets C004 on `to` as well as `from`.

Every C004 that rc.4 reports is still reported, and the same comparison
twice in one copy is reported once. A program that checked clean may now
warn, and fail `--strict`. Warning texts are unchanged.

**New entry points** (#69), additive: the WebAssembly method
`WebReactiveSession.dispatch_view_outcome(event, payload)`, natively
`dispatch_view_outcome_json`, and the kit's `session.dispatchView`. A runtime
given to `createRuntime` without the method works as before; only
`dispatchView` throws `CaveatError` of kind `"load"` on it, leaving the
session untouched.

**Unchanged.** `dispatch`, `dispatch_outcome`, `dispatch_view`, `snapshot`,
`view`, `save` and `restore`, their outputs and the dispatch schema. Checked
against the published rc.4 package, installed offline:

- **Saves.** One session on each runtime played the same events: every send
  in the 44 tracked scenario files (324 scenarios); the Glowcap replay,
  Glowcap with 16 mushrooms and the Glowcap resume stream; the agent ledger's
  session; Trail Rescue's 24 scenarios; and a seeded random stream of 120
  events on each of the 80 tracked programs that open. That is 58,414
  events, with 4,737 saves along the way. Every outcome was the same text on
  both, and every save the same bytes. Each rc.4 save restored on rc.4 and
  on rc.5 to the live session's snapshot, view and save, and the two restored
  sessions then gave the same outcomes on the next events (31,267 in all).
  Each rc.5 save restored on rc.4 too.
- **The command.** `caveat check`, `test` and `validate` give the same output
  from rc.4's package and from this candidate on every tracked program and
  scenario file, apart from the runtime identity in `test`'s report: 106
  programs (80 load, with 7 C001 and 4 C003) and 44 scenario files.
