# CAVEAT Language 1.4.1

**Candidate, not yet published.** This note becomes the release record once
npm publication of caveat-lang@1.4.1 is verified.

1.4.1 is a patch release of 1.4.0. It is cut from `main` and contains two
runtime fixes, D025 and D026, and nothing else. It adds no language syntax,
schema, runtime operation, field, CLI flag, export, MCP tool or tool argument.
It adds one refusal code, `limit/text_limit`, for an input that ended the
session before, as the
[compatibility commitment](https://github.com/WSattazahn/caveat-lang/blob/main/docs/COMPATIBILITY.md)
allows. A save written by 1.4.0 restores on 1.4.1, and a save written by
1.4.1 restores on 1.4.0.

## A value read through a decision carries `withdrawn` (D026)

[Withdrawal 0.1](https://github.com/WSattazahn/caveat-lang/blob/main/spec/caveat-withdrawal-0.1.md)
says that once evidence is withdrawn, every current value whose lineage
includes it carries the `withdrawn` caveat. A value read through `latest(D)`
did. A value read through `committed(D)`, `reopened(D)` or `in_basis(D, E)`
listed the withdrawn evidence but did not carry the caveat, so
`bind status = "in force" when committed(d)` gave no sign that the decision's
basis had been withdrawn. This was so in every release since 1.0.0.

In 1.4.1 those values carry `withdrawn` when the decision's basis lists
withdrawn evidence. The decision's frozen basis, grounds and caveats are
unchanged, and so are `rests_on_withdrawn` and `has_caveat`. A revision
committed after the withdrawal holds its predecessor's basis in its lineage,
so `explain` now shows it "also carrying, through its lineage: withdrawn",
and its commitment basis lists `withdrawn` among its caveats and retained
caveats, as it already listed that basis's other caveats. A program that
withdraws nothing a decision's basis lists is unchanged.

The [corpus sweep](https://github.com/WSattazahn/caveat-lang/blob/main/experiments/d026-sweep/RESULTS.json)
runs 181 programs on 1.4.0 and 1.4.1: 168 are identical and 13 differ only by
`withdrawn`, with no event accepted or refused differently. Saves of
withdraw-then-recommit sessions restore in both directions between 1.4.0 and
1.4.1 and accept and refuse the same further events. The rc.15 departure gate
lists the 11 programs whose save digests change.

## A text past its limit is refused, not fatal (D025)

A text value an event computes, in a rule guard, an effect, a procedure
argument or an active binding, may hold at most 65,536 bytes. Past that, 1.0.0
to 1.4.0 ended the session with a fatal `unclassified` error. 1.4.1 refuses the
event as `limit/text_limit` with the same message, and the session goes on, as
it does for `provenance_limit` and `evaluation_limit` since 1.4.0. The cap is
unchanged, and a text literal past it still fails to load
([Dispatch 0.1](https://github.com/WSattazahn/caveat-lang/blob/main/spec/caveat-dispatch-0.1.md)).
This was the last fatal fault a program could reach, so the kit's fatal-path
test now injects its fault. The save sweep over every tracked program is
byte-identical with 1.4.0.
