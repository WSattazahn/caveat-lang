## The compatibility commitment is now the promise

[COMPATIBILITY.md](https://github.com/WSattazahn/caveat-lang/blob/main/docs/COMPATIBILITY.md) was "proposed for 1.0.0". From this
release it is the promise for every 1.x release:

- **Stable:** the language and what an accepted program computes, decides,
  refuses and explains; dispatch outcomes and the 19 rejection codes; the CLI
  with its exit statuses and `--json` output; the library exports, including
  `./starter` and `./starter/node`; `serve`; the five MCP tools; every named
  schema; and saves and archives as that file states them.
- **Not stable:** see "What is not stable" in COMPATIBILITY.md. Among them are
  the games, `./runtime/*` paths, host conformance, the native Rust API,
  diagnostic and message text, timing, memory and sizes, and the verification
  record.
- **Versioning:** a 1.x patch makes behavior match a documented promise; a 1.x
  minor only adds; only 2.0 removes, renames or changes the meaning of
  anything stable.

The kit README no longer lists "a stable release" under "Not yet", and the
starter guide no longer says its interface may change before 1.0.

## Changes since rc.20

- **`caveat_dependents` says what a subject can be.** Its description now
  states that subjects are causes only (evidence, a reading stream or a
  caveat) and that a claim or decision name is refused with exit code 2,
  because a claim causes nothing and a decision's grounds are evidence. The
  report's `claims` lists the evidence that supports or opposes each claim,
  which is where a trace from a claim starts. The input schema, annotations
  and behavior are unchanged.
- **Comparing several candidates** ([#222](https://github.com/WSattazahn/caveat-lang/issues/222)).
  The authoring guide and the kit reference now point to `for KIND as $NAME`
  for candidates that get the same readings, such as hosts or runtimes, with
  an example that routes one event to each candidate's stream.
- **Revising a program while the record continues** ([#224](https://github.com/WSattazahn/caveat-lang/issues/224)).
  The authoring guide says how to keep each program version beside the range
  of events it governed, and why a save cannot carry a session across a
  revision.
- **Stable GitHub release.** The release workflow marks a release candidate
  tag as a prerelease and a stable tag such as `v1.0.0` as a full release. Its
  annotated-tag and exact-tarball checks are unchanged.
- **Stabilization evidence.** The
  [release-readiness exercise](https://github.com/WSattazahn/caveat-lang/blob/main/experiments/release-readiness/README.md)
  (PR #232), the Gateway verification and the
  [readiness audit](https://github.com/WSattazahn/caveat-lang/blob/main/docs/releases/v1.0.0-readiness-audit.json) (PR #233) are recorded.

## Upgrading

- **From rc.20:** nothing to change. Programs, events, saves and tool calls
  behave the same.
- **From an earlier release candidate:** the rc.17 to rc.20 records list what
  each changed. CI restores saves written by rc.17 through rc.20 with this
  runtime.
- **Same source, always.** A save restores only under the exact source text it
  was made under. A host that revises its program replays its events under the
  new program or starts new sessions.

## Known limits

These are in COMPATIBILITY.md under "Limits" and are not defects. Windows and
collection do not bound a save, and event time is not constant; hosts set and
test their own budgets. Caveat records the evidence supplied to it; it does not
authenticate evidence, saves or archives.
